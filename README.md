# 3GPP Search engine

Информационно-поисковая система по спецификациям 3GPP (релиз 17). Состоит из двух частей:
- `data-prep/` — Python-модуль предобработки данных;
- `search-engine/` — поисковый движок на Go, основа проекта.

## Датасет

Файлы 3GPP обычно выкладываются в формате pdf либо docx, но достаточно много есть тех, кто занимался созданием
вопросно-ответных систем, на их основе, поэтому на Hugging Face есть достаточно хороший датасет, в котором файлы
представлены в виде MD-файлов. Именно он и используется в данном случае. Используется только один конкретный 17 релиз,
т.к. практического применения в датасете сразу с несколькими релизами нет.

## Data-prep

Небольшой модуль на python, который извлекает данные из MD-файлов, пытается произвести небольшую очистку,
после этого результат делит на чанки и сохраняет в jsonl файл, на основе которого потом и будет строиться
поисковый движок.

### Запуск

```bash
python main.py --input ../data/3gpp-specs --output ../data/corpus.jsonl
```

Полезные флаги: `--max-words` / `--min-words` — границы размера чанка (350/20 по умолчанию), `--only` — фильтр по имени файла.

### Описание файлов

- `main.py` — точка входа. Собирает `*.md`-файлы, оставляет только свежие версии, через `parse`/`build_chunks`
  извлекает блоки и нарезает текст на чанки, пишет их в `.jsonl`.
- `extract.py` — разбор одного MD-файла на структурированные блоки: распознаёт заголовки (ATX/Setext), таблицы,
  ASN.1-код, приложения, ссылки и т.п., возвращает метаданные спецификации и список блоков.
- `chunk.py` — превращает блоки в чанки: строит иерархию секций, отбрасывает преамбулу и лишние разделы
  (change history, foreword), режет длинные секции по `--max-words` и генерирует `id` каждого чанка.

## Search-engine

Ядро проекта, написано на Golang. Загружает `.jsonl`-корпус, строит инвертированный индекс и выполняет
булевы запросы с оптимизацией плана исполнения.

### Запуск

```bash
cd search-engine
go run ./cmd/main.go -corpus ../data/prep-specs-1.jsonl
```

Флаги: `-corpus` — путь к корпусу, `-limit` — сколько результатов показывать для каждого запроса.

### Архитектура

`data_reader` загружает документы из `.jsonl` → `analyzer` токенизирует текст → `index` строит инвертированный
индекс (мапу «терм → posting list») → `query` задаёт запрос деревом узлов → `planer` оптимизирует дерево и
компилирует его в итераторы → `exec` исполняет булевы операции над posting lists.

### Описание файлов (отсортированы в порядке использования)

1) `data_reader.go` — чтение `.jsonl`-файла с прошлого этапа. `Doc` — структура документа
   (`search-engine/data_reader.go#L11`) с полями `id`, `spec`, `version`, `clause`, `path`, `text` и др.,
   соответствующими JSON-полям чанков. `Load(path)`/`Read(r)` построчно декодируют файл в `[]Doc`.

2) `analyzer.go` — токенизация текста и термов запроса. Правила: слова берутся по пробелам и очищаются от
   пунктуации; точка между цифрами (`5.3.5.1`) и буквы с цифрами (`5G`, `SIB1`) не разделяются; всё приводится
   к нижнему регистру. `Tokenize` разбивает текст документа на уникальные термы, `QueryTerm` нормализует терм запроса.

3) `index.go` — построение инвертированного индекса. `Index` (`search-engine/index.go#L13`) хранит список
   документов и мапу `term → posting list`. Документы предварительно сортируются по скоринговой функции
   (`ScoreFunc`, по умолчанию L0 — обратная зависимость от позиции), затем `Build`/`BuildWith` проходят
   по ним через `Tokenize` и формируют posting lists. Методы `Postings`, `Doc`, `DF`, `GetStatics` отдают
   posting list по терму, документ, document frequency и статистику индекса.

4) `iterator.go` — базовый итератор по posting lists. `Iterator` — интерфейс (`search-engine/iterator.go#L22`)
   с методами `CurDocID`, `Next`, `Advance`. `ListIterator` (`search-engine/iterator.go#L11`) обходит
   отсортированный список DocID: `CurDocID` — текущий DocID (или `NoMore`), `Next` смещает указатель вправо,
   `Advance(v)` бинарным поиском ищет первый DocID `>= v`.

5) `query.go` — ноды запроса как базовые элементы для описания булевых операций и термов. `TermNode` — одиночный
   терм, `AndNode`/`OrNode` — списки дочерних нод, `AndNotNode` — пара «включить/исключить». Конструкторы
   `Term`, `And`, `Or`, `AndNot`; метод `String()` воспроизводит запрос в инфиксной нотации.

6) `planer.go` — оптимизация плана запроса и компиляция его в итераторы. `Optimize` рекурсивно обходит дерево,
   нормализует термы и оценивает стоимость поддеревьев по `DF`: для `And` дети сортируются по возрастанию
   стоимости (самый селективный терм идёт первым), для `Or` стоимости складываются. `Compile` оптимизирует
   дерево и через `build` превращает его в конкретные итераторы.

7) `exec.go` — итераторы под каждую булевую операцию. `Drain` вычитывает все DocID из итератора, `Empty` — пустой
   итератор. `IterAnd` через `Advance` заставляет все итераторы смотреть на один DocID; `IterOr` выбирает
   минимальный DocID среди текущих позиций; `IterAndNot` идёт по DocID включённого итератора и проверяет,
   что его нет в исключающем.

8) `cmd/main.go` — демонстрационная CLI. Загружает корпус, строит индекс, печатает статистику и для каждого
   запроса из `demoQueries` выводит оптимизированный план, найденные документы и сниппет (первые 200 рун текста).
   Запросы задаются через конструкторы `Term/And/Or/AndNot`.
